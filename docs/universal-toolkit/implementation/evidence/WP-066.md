# WP-066 — Plugin browser and rack

**State: accepted after integration.**

Luna's `work/wp066-plugin-ui` lane was integrated as `33e497a`. `PluginBrowser`
offers query/kind/category filters, availability and scan status, and
add/preview requests. `PluginRack` draws host ordering, bypass and error
states, latency, and parameter/editor actions; drag and arrow gestures
request reordering. Add/reorder/bypass/remove outcomes use explicit host
acknowledgments. The fixture uses mock snapshots and does no plugin loading.

The isolated configured-limit build, focused QML run (4/4), preview check,
dump and inspected screenshot passed. The merged focused run passed 4/4 and
`example_plugin-host` passed. The merged dump placed both controls at
574×615, with the rack list at 566×592. I opened and inspected the
[merged plugin fixture](WP-066-plugin-ui.png).

Fixes made in this run:
- **Relocatable host lookup** (under WP-088's relocatability decision D-202, which names plugins). `libqindatk` had the build tree's and
  the install prefix's absolute host paths compiled in. It now finds
  `qindatk-plugin-host` relative to its own file (`dladdr`): the build tree's
  `libexec/` next to a `CMakeFiles/` folder, or `<libexecdir>/qindatk/` in an
  install. `strings` over the debug-stripped library shows no worktree path.
  `qtk-preview --dump` with `QINDATK_PLUGIN_HOST` unset shows
  `AudioPluginRegistry.hostExecutable` = `…/build/cf/libexec/qindatk-plugin-host`.
- **Killed host processes are reaped before deletion.** `fail()` deleted the
  `QProcess` right after SIGKILL. `~QProcess` warned ("Destroyed while process
  … is still running") and blocked on the wait. The process is now deleted on
  `finished`, and the instance destructor reaps any still pending.
- The test plugins' `clap_entry` definitions no longer repeat `CLAP_EXPORT`,
  which `clap/entry.h` already declares; GCC warned that it ignored it. The
  symbol is still exported (`nm -D`).
- A rack parameter row shows the host's `displayValue` when its binding has no
  value text yet, where it showed nothing before.
- The `plugin-host` example's fixture host rejects **Reload** for a plugin
  that is still not installed, instead of acknowledging it silently.

### Audit gap closure (2026-09-25, `build/cf`, `-j12 -l12`)

An independent audit at `38f0392` found three gaps. Each now has real
behaviour and a test with real CLAP binaries:

1. **Reorder (Req 4, AUD-17) had no proof.** New
   `tst_audio_plugin_chain::reorderChangesProcessingAndKeepsTheInstance`.
   On a MIDI track the test instrument replaces its input and Gain halves
   it, so `[Synth, Gain 0.5]` plays the note at exactly 0.125 and
   `[Gain, Synth]` at 0.25. `movePlugin` within the channel changes the
   rendered samples accordingly. Moved to an audio track, Gain halves that
   track sample for sample. The instance keeps its process ID, its
   `AudioPluginInstance`, its parameter IDs (`<instance>/1`, `/2`), its
   automation breakpoints and its saved state (Gain 0.5 in the state blob).
   A refused move changes nothing. The reordered chain is saved and reopened
   in a new session with the same order and identical samples, and it
   reorders again after the reopen. Mutation check: running the inserts in
   reverse order fails this test at frame 12000 (0.433 against 0.308).
2. **Rack/browser glue was unexercised (Req 4).** `PluginBrowser` and
   `PluginRack` gained a `host` property (`host: session.plugins`,
   `PluginBrowser.targetChannelId`). The views then read rows and scan
   status from the real host, and each request runs `rackAction()` and is
   acknowledged with its answer; the request signals still fire first.
   `tst_audio_plugin_chain::rackActionDrivesTheHost` drives every action:
   add (with `index`, bad channel, unknown plugin), reorder (in the channel
   and to the master), bypass, edit-parameter (`value`; `displayValue`
   " 1.5 " parsed and rendered as exactly 1.5 × input; refused for "loud",
   another instance's parameter, a malformed ID and a read-only parameter,
   none of which reach the parameter), open-editor and close-editor with the
   owner window, reload (live: same process; failed: a new one), remove,
   and an unknown action. New `tst_plugin_host_session.qml` (6/6) runs both
   controls on a real `Tk.AudioSession`. It scans the test plugins through
   the `pluginFixtures` that `tst_qml.cpp` provides, clicks **Add**, and
   reorders, bypasses, edits (the Knob's binding is the host's), reloads and
   removes through the host. `examples/plugin-host` is now a live host: a
   session with a Voice track and the plugins found on this machine; its
   smoke test sets `CLAP_PATH` to the test plugins. The fixture host is gone.
3. **Automation over time on a plugin insert (D-191) had no fixture.** New
   `tst_audio_plugin_chain::automationCurveDrivesThePlugin`: the Gain lane
   has breakpoints 0 → 2 over 8192 frames and 2 → 1 by frame 12288. Every
   rendered sample equals `curve(block start) × input` exactly, with block
   starts 256 frames apart, and the gain changes at 48 block starts.
   Mutation check: evaluating the curve at time 0 fails this test at
   frame 256.

Found and fixed while running the suite:
- **A crash could be reported as a hang.** `tst_audio_plugin_engine::crashAndHangDuringPlaybackLeaveTheSessionPlaying`
  failed in the ctest run, and in 3 of 12 runs under CPU load, with "stopped
  responding" instead of "crashed". The cause was systemd-coredump
  (`core_pattern` is a pipe): the crashing test plugin stayed alive while its
  core was written, longer than the 300 ms hang limit. The test plugins now
  crash without a core dump (`PR_SET_DUMPABLE` 0). This also stops each test
  run from adding core dumps to the journal (54 had accumulated). The hang
  poll now collects an exit the event loop has not delivered yet before it
  calls a plugin hung (`AudioPluginInstance::exited()`). Result: 20 of 20
  runs passed under the same load, and no new core dumps were written.

**Accept when.** CLAP is the one declared format and has the lifecycle,
audio and state fixtures above. LV2 and VST3 are declared unavailable, not
advertised, so they owe no evidence; a later adapter brings its own.

**Scope notes.** LV2 (lilv is not installed and is not a dependency) and
VST3 (SDK absent) adapters are not built. Not supported by the CLAP host:
side-chains, surround and 64-bit ports, transport information for plugins,
sample-accurate automation inside a block (values change at block starts,
at most 256 frames apart), presets (`PluginBrowser` preset preview stays a
host request), a shared host process for several instances, and Wayland
editor embedding. Editor embedding on a real X server and window-manager
focus behaviour, performance measurement (per-instance process and context
switch cost), other platforms, screen-reader runs and translation belong to
WP-088 to WP-094.
