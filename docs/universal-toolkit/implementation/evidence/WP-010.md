# WP-010 — Typed contracts and capability discovery

**State: accepted at the contract and installed-consumer level.** Accepted dependencies WP-004 through WP-007 are integrated
at `3d811b7`. Sol owns the public record and registry API. Luna's read-only
survey confirmed that the core `QindaTK` QML module and `QindaTK::qindatk`
export already provide a base for separate optional pack targets; it found no
general adapter registration mechanism in the existing source.

## Implemented contract

`application_contracts.h` defines distinct EntityId/DocumentId types,
RevisionId, UnitQuantity, ExactTime, ColorValue, structured errors and
validation issues, immutable versioned snapshots, command/edit request
contexts and
thread-safe cooperative cancellation tokens. `ContractCodec` transfers
revision/generation/time integers as decimal strings and rejects numeric QML
values, malformed decimals and overflow. Request acceptance rejects a stale
document, schema, revision, reset generation or cancelled token.

`CapabilityRegistry` stores explicit lightweight per-operation metadata,
including disabled reason, backend ID/version and priority. Querying metadata
has no engine factory or load path. Resolution first prefers availability,
then higher priority, then stable backend ID. A backend can replace its own
entry or remove all entries. `CapabilityBinding` updates QML properties when
the selected operation changes and remains safe when the registry is
destroyed. The [contract guide](../../../application-contracts.md) and
[D-026](../../../decisions-application.md#d-026--keep-application-contracts-typed-and-optional-engines-explicit)
set GUI/worker/render/realtime ownership and optional-pack boundaries.

## Verification so far

- Integrated Debug builds using the live configured `MAKEOPTS=-j24 -l24`
  succeeded on Qt 6.11.1 and Qt 6.8.3. Full CTest passed **22/22 on each**;
  the two added C++ targets cover codec precision, invalid input,
  cancellation/reset, per-operation status, unavailable reasons, fallback,
  notification and registry destruction. `all_qmllint` exited 0 on each
  version. Nonfatal existing lint warnings remain in ignored build logs
  `build/integration/wp010-lint.log` and `build/qt68/wp010-lint.log`.
  A final additive public context-record and cancellation-guard header edit
  rebuilt on both versions; the two affected contract/registry tests then
  passed **2/2 on each**. No QML control or registry behavior changed in that
  final header edit.
- The catalog generator now reports 105 QML types, adding
  `CapabilityRegistry` and `CapabilityBinding`; regeneration is deterministic.
- An isolated installed-prefix consumer linked only `QindaTK::qindatk`,
  imported `QindaTK as Tk` and exercised a disabled PDF export button with a
  specific reason that becomes enabled after an explicit manifest update.
  It sent a revision above 2^53 through a QML string property without loss.
  While export was unavailable it wrote and reloaded an immutable snapshot's
  opaque unknown-content bytes and exact header through a local temporary
  file; both remained unchanged after capability publication. This is a
  contract-level preservation fixture, not a document-manager serializer.
  The consumer has no optional engine target or loader; `ldd` showed core
  QindaTK and Qt dependencies only. Sol reran the offscreen installed consumer
  successfully after reviewing the fixture.

## Acceptance boundary

APP-20 and ENG-01 are satisfied as foundation contracts: a real installed
consumer can query per-operation status, disable an unavailable action with a
reason, retain opaque unsupported content, and exchange typed/versioned
records without integer loss. Invalid manifests, unavailable operations and
stale/cancelled requests have negative tests. No asynchronous job queue,
domain provider or large data cache is implemented in this package; their
scale/cancellation and fidelity gates belong to their owning later packages.
The first optional pack must verify its separate target/install/discovery
implementation against D-026. Full document recovery, actual PDF export and
native platform/input qualification remain with WP-013, WP-019 and WP-092.
