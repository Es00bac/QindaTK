## Audit gap fixes (2026-09-25)

An independent audit put the package at about 80% and found eight gaps. Each
was re-checked against the plan (WP-082 items 1–5) and the code, and all
eight were real. What changed:

| # | Audit finding | Fix | Test that fails without it |
| --- | --- | --- | --- |
| 1 | Undoing a `Create` deleted the object even after another actor edited it, hiding their committed edit (breaks D-169) | Supporters carry `(time, actor)`; undo of a create refuses with `undoConflict` when another actor's winning value, text edit or revival is newer than the create | `tst_collaboration_domain::undoOfCreateKeepsCollaboratorEdit` |
| 2 | `textEdit` applied the delete, then failed the insert and queued nothing: a delete no other replica ever sees | Every limit (sequence size, queue, log space) is checked before the first part applies; applied parts are always queued; long inserts go out as chained ≤4,096-unit chunks | `tst_collaboration_domain::failedTextInsertLeavesNoUnsentDelete` |
| 3 | Lifetime cap of 4,096 operations / 4 MiB, no compaction; an edit past the cap stayed visible only in memory. The WP-093 scope note was wrong | Authoritative (hub) services compact into a replica-state base (D-295), also headless via `setCompactionBaseline`; replicas rebuild from base + log + own queue; socket peers adopt each new base and keep their outbox; a connected edit the store cannot hold is refused before it applies or taken back; store format 2 (reads 1) | `tst_collaboration_compaction` (4,400 edits past the cap; offline, late and reopened replicas; redelivered folded operations; headless hub; refused edit taken back), `tst_property_sync_recovery::peersAdoptTheHubBaseLiveAndAfterBeingOffline` |
| 4 | 64-checkpoint cap stopped restore for good; restore refused text over 4,096 units and snapshots over 40 KiB | Both histories keep the newest 64 (restore's safety version evicts the oldest); `remove(id)` for local versions; local snapshots up to 1 MiB; a restore larger than one packet splits into several `Restore` operations by object; text restores replace only the differing middle, in chained inserts | `tst_property_version_history::historyKeepsTheNewestVersionsSoRestoreNeverStops`, `::restoresVersionsLargerThanOnePacket` |
| 5 | An edit refused by the hub (offline edit before a downgrade) stayed applied and was resent forever; docs said "the host must discard" | Rejects carry `permanent`; the bridge discards a permanently refused operation from the store's outbox and rebuilds local replicas (`operationDiscarded`, D-296); transient refusals stay queued | `tst_property_sync_recovery::offlineEditRefusedAfterDowngradeIsDiscarded` |
| 6 | No public way to turn a text element ID into a position, so a remote selection could not follow edits | `textAnchor` / `textPosition` on the client (D-206); docs tell `PresenceLayer` mappers to resolve anchors with it | `tst_collaboration_domain::remoteSelectionFollowsEditedText` |
| 7 | Presence never crossed between the hub's own replicas and socket peers | The service emits `presencePublished` and accepts `relayPresence`; the server bridges both ways, including the snapshot on connect and leaves | `tst_property_sync_network::hubPresenceReachesPeersBothWays` |
| 8 | Fault fixture had no Restore/Checkpoint/undo operations; no TCP session was closed by a bad frame and then shown to converge | The shuffled/duplicated/dropped fixture now includes Restore (revival, per-key winners), a shared checkpoint and undo/redo operations; a TCP relay tampers, drops and replays one frame each, and every session ends and then converges after reconnect | `tst_collaboration_domain::faultFixtureConvergesAfterReplay`, `tst_property_sync_recovery::tamperedDroppedOrReplayedFrameEndsSessionThenReconnectConverges` |
